«прочитано агентом» это разные вещи:

- **[ПРОВЕРЕНО]** — я лично прочитал код в этой сессии и/или воспроизвёл

записано, **что** тут произошло, чтобы третья ветка вывода не завела

### ECON-3 — EMA дани не может расти; дорогие малочисленные позиции не облагаются НИКОГДА `NOFIX`
**[ПРОВЕРЕНО]** — `src/macro/world_tick.cpp:127-133`

```cpp
lm.titheAvgGoods[c] += (count_of(c) - lm.titheAvgGoods[c]) >> 5;   // kTitheAvgShift
```

Арифметический сдвиг вправо на 5 округляет **вниз**: любая положительная
разность `< 32` даёт `0`, любая отрицательная даёт `−1`.

- позиция, чей запас никогда не превышает 31, имеет `titheAvg == 0`
  **вечно**: `(31 − 0) >> 5 == 0`. Дань по ней — `0 >> 3 == 0` (`:139`).
  Украшения, статуи, резьба, инструменты в деревне **не облагаются никогда**;
- среднее насыщается на `count − 31`, а не на `count`: подъём требует
  разности ≥ 32, спад идёт при разности ≥ 1. **Храповик вниз**;
- при `count == avg` спада нет, при `count = avg − 1` среднее падает на
  1/день — асимметрия ×32.

Комментарий `:120` («Signed shifts floor toward the value from either
side») описывает симметрию, которой нет.

**Отказ:** сюзерен систематически недополучает дань, а по «дорогим и
малочисленным» позициям — ровно ноль. Это тот самый класс, который
правка v73 («по 1/8 каждого запаса») чинила для серебра.

*Вердикт владельца 2026-09-09: **не проблема, это замысел.** Мелкий запас
не облагается, и целочисленный пол честен: 1/8 от 4 это 0, а не 1.
Предложенную починку (хранить среднее в 1/32, то есть `avg×32`, чтобы оно
могло расти с малых чисел) владелец отклонил вместе с вариантом «ненулевой
запас облагается минимум единицей». Правки нет; описание арифметики выше
остаётся верным и служит заметкой баланса, если сюзеренская экономика
когда-нибудь окажется беднее задуманного.*

**Комментарий на месте — ИСПРАВЛЕН 2026-09-09.** Строка `world_tick.cpp:121`
(«Signed shifts floor toward the value from either side») обещала
симметрию, которой нет: это единственное место, где объявленный замысел
был записан неверно, и после вердикта оно стало опаснее самой
асимметрии. Теперь там записано, **что** несимметричность — вердикт, а не
недосмотр; **чем** платят (среднее садится на горизонт ниже правды, стак
≤ 31 не облагается никогда); и **почему симметричный шаг был бы хуже** —
мёртвая зона ±31 в обе стороны вместо точного слежения вниз. Плюс главное:
целое поле с шагом 1/32 не выражает среднее мелкого запаса — это вопрос
**разрядности, а не округления**, и никакое правило округления его не
решает (хранение предмасштабированного среднего решило бы, и отклонено).
Поведение не тронуто, свидетель не нужен.

### SMOKE-5 — `dungeon_cave`: устье найдено, но `interact()` не открывает его `P1`
**[ЗАМЕРЕНО]** — `src/app/smoke.cpp:2572-2580`

### SMOKE-7 — Три макро-временны́х сценария краснеют В СВИПЕ и зелены поодиночке `P1`
**[ЗАМЕРЕНО]** — свип после правки `SAVE-1`, 2026-09-09

Контрольный свип после правки дал три красных, которых не было в базе:
`macro_recovery` (сиды 1, 7, 999), `chronicle_rate` (12345, 1, 7),
`macro_travel_sp` (999). Пути загрузки в них нет вообще — правка их
касаться не может. И действительно:

```
в свипе:      macro_recovery minutes=0  hp=1 mp=0 sp=0
поодиночке:   macro_recovery minutes=6  hp=2 mp=1 sp=1     ← 3 сида из 3
в свипе:      chronicle_rate day=1->1 factsInDay=0
поодиночке:   chronicle_rate day=1->2 factsInDay=3782      ← 3 сида из 3
в свипе:      macro_travel_sp frames=600 left=4  pos=80,185->80,185
поодиночке:   macro_travel_sp frames=175 left=0  pos=80,185->77,182
```
Симптом у всех один: **мир не получил времени**. И секундомер свипа это
подтверждает — `chronicle_rate` в зелёных прогонах занимает 8-9 с, в
красных 3-4 с; он не «шёл и не дошёл», он ушёл рано.

Что проверено и **не** воспроизводит: одиночный запуск (7 из 7 зелёных),
серия из трёх повторов пары (6 из 6), десять CPU-загрузчиков параллельно
(зелёный), **и ещё один полный свип 240 прогонов с расставленной ловушкой
— все три зелёные** (`chronicle_rate` 9-10 с, здоровая длительность). Итог
по трём полным свипам: мигание случилось в одном из трёх.

**Механизм сужен чтением, 2026-09-09.** «Мир не получил времени» не может
означать нехватку машины: `advance_sim_steps` (`main.cpp:3491`) крутит
ровно N шагов и не имеет бюджета реального времени. Значит каждый из N
шагов был отбит **гейтом паузы** (`world_paused`). Из четырёх его причин
одна исключена по коду: `set_paused` (`main.cpp:2291`) первой строкой
делает `if (app.smoke.enabled) return`, то есть под харнессом ручная пауза
невозможна — случайная клавиша её не ставит. Остаются **панель** и
**модалка**; `state != Playing` тоже исключён, потому что
`smoke_boot_invariants_hold` требует `Playing` перед запуском сценария.

**Поставлена ловушка на будущее** (`main.cpp`, `advance_sim_steps`): если
промотка не купила ни одного тика, а мир при этом в `Playing`, печатается
маска причин — `[pause] ... mask=xx player=? panel=? modal=? menu=?`.
Молчит вне `Playing` (на сплэше промотка законно не покупает времени, и
диагностика, которая кричит там, приучает себя игнорировать). Следующее
срабатывание назовёт причину само.

**Практический вывод, важнее причины:** у этих трёх свидетелей красный
цвет **не является утверждением о коде**. Красный из свипа обязан быть
перепроверен одиночным прогоном, прежде чем на него сошлются. Это пятый
класс к списку `broken-smokes`.

## 15. ПРЕДЛАГАЕМЫЙ ПОРЯДОК РАБОТЫ

Вопрос владельца: «по сессии на каждую проблему — это самое безопасное?»

**Не самое.** По сессии на каждую находку — это ~60 сессий, и оно
безопаснее только для **структурных** правок. Для остальных сессия — не
единица безопасности; единица безопасности это **один коммит, который
можно откатить, с зелёным `ctest` + смоуками**.

Предлагаю три режима, по классу правки:

### Режим A — «одна сессия, одна правка» (строго)
Правки, которые **меняют поведение мира** и требуют нового свидетеля:

`SAVE-1` · `ECON-1`+`ECON-2` (одна правка) · `ECON-3` · `AI-1` ·
